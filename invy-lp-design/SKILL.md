# invy 紹介LP デザイン（構成案 → デザイン → Figma／CMS）

クライアントの紹介LPを、Claudeと壁打ちしながら組み立てる。最終的な着地は **invy CMS への入稿**。
Figma はデザイナーへの受け渡し用の中間成果物で、CMS に入らないデザインは作らない。

**中核の原則：構成は CMS のテンプレートパーツだけで組む。** カタログ外のパーツを勝手に足さない。
カタログで実現できない要望は、デザインに混ぜずに「CMS外の要望」として別に書き出す。

**出力は4枚：紹介者ページ／ゲストページ／OGP 画像／LINE で送ったときの見え方。**
見た目は `campaign-design-dip` の紹介ページ画面と同じ型（色面のヒーロー＋吹き出し、白の角丸カード、リボン見出し＋大きな数字の特典、
チェック付きのポイント、番号付きのステップ、塗りの CTA）で、スマホの枠は付けない。すべて Figma に取り込める SVG で出す。

**もう一つの原則：spec.json が正、SVG・入稿シート・プレビューはその表現。**
修正は必ず spec.json を直してから再ビルドする。書き出したSVGやシートを手で直さない（次のビルドで消える）。

## 実行前に必ず読む

| ファイル | 内容 | いつ読む |
|---|---|---|
| `references/01-process.md` | 壁打ちの工程【0】〜【7】と、止まるポイント | 最初に必ず |
| `references/03-cms-blocks.md` | CMS ブロックカタログ（使えるパーツ・入力項目・画像枠） | 構成を組む前に必ず |
| `references/A-invy-facts.md` | invy の事実と制約（CTA の遷移先・計測方法など） | 構成とコピーを書く前に必ず |
| `references/02-copy-rules.md` | LP の文章規則・禁止表現 | コピーを書くとき |
| `references/04-output.md` | spec.json の書き方、ビルド、Figma 取り込み、入稿シート | spec を書く・書き出すとき |
| `references/05-checklist.md` | 書き出し前チェック | 書き出す前に必ず |

`A-invy-facts.md` を読まずに書くと、「このページから予約できる」のような invy の提供範囲を超えた導線が生まれる。

## 手順

1. **参照ファイルを読む**（上の表の「必ず」のもの）
2. **入力を確認する**（【0】）。足りない情報は一度にまとめて聞く。聞いても埋まらないものは仮説で置き、仮説であることを明示して進む
3. **前提を整理し、構成案を出す**（【1】〜【3】）。ブロック表（No／CMSパーツ／KEEP・MOD・NEW／このブロックで伝える1点）で提示する
4. **構成案の承認を得る。ここで一度止まる。** コピーやデザインに進まない
5. **コピーを書く**（【4】）。各ブロックの入力項目を埋める
6. **spec.json を書いてビルドし、プレビューを見せる**（【5】）
   ```bash
   python3 scripts/new_spec.py <案件>/spec.json --project "案件名"   # 叩き台（任意）
   python3 scripts/build.py <案件>/spec.json --zip                   # 書き出し
   ```
   既存ページの改修なら、先に `python3 scripts/import_invy.py page.html --spec <案件>/spec.json` で現行構成を取り込む（全ブロック KEEP になる）
7. **壁打ちで直す**。指摘を spec.json に反映して再ビルドし、差分を短く伝える。これを合意まで繰り返す
8. **チェックを通して書き出す**（【6】）。`05-checklist.md` を確認し、zip（4枚の Figma 用 SVG と全部入りの SVG・入稿シート・プレビュー・spec.json）を渡す
9. **ハンドオフを出す**（【7】）。未確定事項・画像素材の依頼・CMS外の要望を、チャット上で箇条書きにして渡す

## 守るべき前提

- 出力幅は実機 375pt × 3 ＝ **1125px** 固定。数値は invy 実機 CSS の3倍（本文42px＝14pt、見出し72px＝24pt、CTA高さ207px＝69pt、左右余白60px＝20pt）。レンダラーの数値を崩さない
- 配色は積極的に付ける。`primary`（CTA・強調）と `secondary`（ヒーロー・リボン）の2色をクライアントのブランドから決め、淡色・濃色はレンダラーが自動で作る。色が決まらないときは既定の配色（scarlet × sky）で出し、ワイヤーは依頼されたときだけ `mode: wire` にする
- 色は **CMS で入れられる手段の範囲だけ** で当てる（背景色＝スタイル設定、文字色＝リッチテキスト、ボタン色＝head の CSS）。KV など作り込む部分は画像で入れる前提にする。詳しくは `03-cms-blocks.md`「色の変え方」
- 同じ動きのボタンは同じ色・同じ形にそろえる（LINE で送るボタンはどこでも LINE の緑）。紹介フォームの送信ボタンは縦並び・全幅が標準
- デザイン上に作業用の表示（ブロック番号、KEEP/MOD/NEW バッジ、注釈）を描かない。状態と意図は入稿シートとプレビューの表に出す
- 画像はクライアント支給の素材だけを使う。無ければ比率つきの画像枠のまま渡し、ハンドオフで素材を依頼する。画像を生成・捏造しない
- 事実確認が要ること（特典の条件、計測方法、遷移先の URL、CMS の推奨画像サイズ）を推測で確定させない。未確定として残す
- HubSpot などのコネクタでクライアント情報を調べる場合は、組織の接続先確認ルールに従う

invy-lp-design/
├── SKILL.md
├── references/
│   ├── 01-process.md        壁打ちの工程
│   ├── 02-copy-rules.md     文章規則
│   ├── 03-cms-blocks.md     CMS ブロックカタログ（catalog.py から生成）
│   ├── 04-output.md         spec.json・ビルド・Figma・入稿シート
│   ├── 05-checklist.md      書き出し前チェック
│   └── A-invy-facts.md      invy の事実と制約

│   ├── catalog.py           ブロック定義（正）。ここを直したら 03 を再生成

│   └── import_invy.py       既存 invy ページの HTML → spec.json
└── assets/
    └── sample_spec.json     記入例
